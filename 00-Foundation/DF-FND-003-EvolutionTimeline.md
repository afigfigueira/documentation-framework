# 1. Before the Framework

---

## 1.1. Introduction

This timeline describes the historical evolution of the **Documentation Framework**, identifying the events that led to its creation and the major transformations that occurred throughout its development.

Unlike the *Research Journal*, which explains the process through which ideas were discovered, this document seeks to answer a different question.

**When did these changes occur, and how did they evolve over time?**

The timeline begins before the framework itself existed.

---

## 1.2. Context

During the early stages of the VisualEngine development, no documentation system existed.

Documentation was created only when an immediate need arose.

It was common to find.

* personal notes;
* README files;
* small technical notes;
* experimental documents.

There was no overall organization.

---

## 1.3. Characteristics

During this phase.

The documentation exhibited several typical characteristics.

* lack of a uniform structure;
* absence of conventions;
* inconsistent naming;
* limited reuse;
* strong dependence on the author.

Each document was created independently.

---

## 1.4. Organization

The organization depended entirely on the directory structure.

For example.

```text

			docs/

			notes/

			temp/

			misc/

```

Directories were used only to separate files.

No semantic organization existed.

---

## 1.5. Observed Problems

As the project grew, several difficulties began to emerge.

Among them.

* duplicated information;
* contradictory documents;
* difficulty locating knowledge;
* lack of traceability;
* complex maintenance.

Initially, these problems appeared to be isolated.

Later, it became clear that they shared a common origin.

---

## 1.6. First Attempts

Small organizational initiatives then began to appear.

For example.

* using consistent titles;
* separating technical and functional documentation;
* creating dedicated directories.

These improvements partially simplified maintenance.

However, they did not solve the structural problem.

---

## 1.7. Documentation Remains Secondary

During this phase.

Documentation was regarded as a by-product of development.

The priority was the code.

Whenever time became limited.

Documentation was postponed.

This culture proved to be one of the main obstacles to future evolution.

---

## 1.8. Project Growth

As the VisualEngine increased in size.

The number of documents grew rapidly.

There was now.

* architectural documentation;
* technical documentation;
* experimental documentation;
* research documentation.

The diversity increased significantly.

---

## 1.9. The First Sign

It was precisely during this phase that the first important sign appeared.

The problems were no longer related to individual documents.

They became related to the documentation as a whole.

The challenge was no longer writing documents.

It was managing documentation.

---

## 1.10. A Change in Perspective

A new idea then began to emerge.

Perhaps documentation should be treated as a system.

Rather than merely as a collection of files.

Although still very immature.

This hypothesis would influence every subsequent stage of the framework's evolution.

---

## 1.11. Situation at the End of the Phase

At the end of this period.

The project presented the following situation.

* existing documentation;
* distributed knowledge;
* no documentation architecture;
* no formal standards;
* increasing maintenance difficulties.

Despite its limitations.

This phase proved to be extremely important.

It clearly demonstrated the need for a completely different approach.

---

## 1.12. Historical Milestone

**The first realization that documentation is an architectural problem rather than merely an editorial one.**

This conclusion represents the true starting point of the Documentation Framework's evolution.

---

## 1.13. Consequences

From this point onward.

The research no longer focused on producing better documents.

It began searching for a better system to produce, organize, and maintain documentation.

This change in objective marked the conceptual birth of the project.

---

## 1.14. Next Stage

With the problem now clearly identified.

The next stage would focus on the first attempts at standardization.

The first document models, writing conventions, and later the **Templates** would emerge, representing the first concrete step toward building the Documentation Framework.

---

## 1.15. Phase Summary

| Aspect | Status |
|---------|--------|
| Organization | Informal |
| Templates | Non-existent |
| Metadata | Non-existent |
| Document Identity | Non-existent |
| Workflow | Non-existent |
| Registry | Non-existent |
| Baselines | Non-existent |
| Document Relationships | Implicit |
| Documentation Architecture | Non-existent |

---

## 1.16. Conclusion

The period before the Documentation Framework was characterized by largely informal documentation, sufficient for small projects but incapable of supporting the architectural growth of the VisualEngine.

It was precisely the accumulation of these limitations that made the need for a dedicated documentation infrastructure evident.

Every evolution described in the following phases can be understood as a progressive response to the problems identified during this initial period.

---

# 2. The First Documentation Attempts

---

## 2.1. Introduction

Once it became evident that informal documentation was no longer sufficient, a period of experimentation began.

The objective was not yet to build a documentation framework.

The goal was simply to improve the organization of the existing information.

This phase was characterized by numerous attempts, some successful and others quickly abandoned.

Although simple, these experiments established the foundations for every subsequent stage of the framework's evolution.

---

## 2.2. Primary Objective

The objective was to reduce the growing disorganization of the documentation.

The first initiatives attempted to introduce some consistency without fundamentally changing the way documentation was produced.

Concepts such as.

* Metadata;
* Document Identity;
* Baselines;
* Registry.

Did not yet exist.

The focus was essentially practical.

---

## 2.3. First Conventions

Small informal rules began to emerge.

For example.

* using more consistent titles;
* dividing documents into sections;
* avoiding duplicated information;
* separating technical documentation from functional documentation.

These conventions improved readability.

However, they still depended entirely on the author's discipline.

---

## 2.4. Directory-Based Organization

One of the first solutions consisted of reorganizing the documents.

For example.

```text

			docs/

			architecture/

			research/

			reference/

			notes/

```

The physical organization became clearer.

However.

It quickly became apparent that different classifications could be equally valid.

Directories solved only part of the problem.

---

## 2.5. The First Templates

Small reusable document models also began to emerge.

They typically included.

* title;
* introduction;
* body;
* conclusion.

Each new document was created by copying an existing one.

True Templates did not yet exist.

But the concept was gradually taking shape.

---

## 2.6. The First Standardization

For the first time.

Several documents began to share a similar appearance.

Although this standardization was primarily visual.

It represented an important step forward.

The documentation started to convey a much greater sense of consistency.

---

## 2.7. The Limitations Become Apparent

As the number of documents increased.

The limitations of informal conventions began to emerge.

For example.

* different authors interpreted the rules differently;
* some documents ignored the conventions entirely;
* new document types required different structures.

Manual standardization proved to be insufficient.

---

## 2.8. The Reusability Problem

Another difficulty soon appeared.

Whenever a model was improved.

Every future document had to be updated manually.

Existing documents remained inconsistent.

This situation clearly demonstrated the need for a reusable mechanism.

---

## 2.9. Knowledge Remains Scattered

Despite the organizational improvements.

Knowledge remained distributed.

Documents continued to exist in isolation.

There was still no.

* common identification;
* formal relationships;
* consistent classification.

Documentation was beginning to grow faster than the ability to organize it.

---

## 2.10. The First Architectural Reflections

It was precisely during this phase that an important change began to emerge.

Documentation ceased to be viewed merely as a collection of texts.

It gradually began to be understood as a system that also required an architecture.

Although this idea had not yet been fully developed.

It would profoundly influence every subsequent stage.

---

## 2.11. The Role of Experience

Many of the decisions made during this phase were later abandoned.

Nevertheless.

None of them were wasted.

Each attempt made it possible to better understand.

* what worked;
* what did not work;
* which problems were truly important.

The research gradually became more systematic.

---

## 2.12. Situation at the End of the Phase

At the end of this period.

The documentation was in a significantly better state than during the initial phase.

There was now.

* more consistent organization;
* basic conventions;
* partially reusable structures.

However, the fundamental concepts that would later define the Documentation Framework were still absent.

---

## 2.13. Historical Milestone

**The first conscious attempt to standardize documentation through conventions and reusable document models.**

Although still far from becoming a documentation framework.

This phase marked the beginning of documentation standardization.

---

## 2.14. Consequences

The limitations encountered led directly to an important conclusion.

Conventions alone are not sufficient.

It was necessary to create reusable and formally defined structures.

This conclusion would pave the way for the emergence of the first **Templates**.

---

## 2.15. Next Stage

The next phase would be dedicated precisely to the development of these Templates.

For the first time.

Documentation would no longer depend exclusively on conventions.

Instead.

It would rely on reusable formal models.

This moment represents one of the first major structural milestones in the evolution of the Documentation Framework.

---

## 2.16. Phase Summary

| Aspect                         | Status         |
| ------------------------------ | -------------- |
| Organization                   | Improved       |
| Conventions                    | Informal       |
| Templates                      | Experimental   |
| Metadata                       | Nonexistent    |
| Document Identity              | Nonexistent    |
| Workflow                       | Nonexistent    |
| Registry                       | Nonexistent    |
| Baselines                      | Nonexistent    |
| Document Relationships         | Implicit       |

---

## 2.17. Conclusion

This phase represents the transition from completely informal documentation to a more structured approach.

Although the adopted solutions were still relatively simple, they clearly demonstrated that documentation consistency could not rely solely on the discipline of individual authors.

The need for reusable mechanisms became evident and led directly to the emergence of the first Templates, which would mark the true beginning of the Documentation Framework architecture.

---

# 3. Emergence of Templates

---

## 3.1. Introduction

Attempts to standardize documentation through conventions alone quickly revealed their limitations.

Although they improved documentation consistency, they remained overly dependent on each author's interpretation.

The next step consisted of introducing **Templates**.

This was the first formal mechanism created specifically to standardize document production.

It also represented the first recognizable component of what would later become the Documentation Framework.

---

## 3.2. Primary Objective

The objective was simple.

To ensure that similar documents were created in a similar way.

The idea was to reduce structural variability without restricting the content itself.

---

## 3.3. The First Templates

The first Templates were relatively simple.

They typically included.

* title;
* introduction;
* chapters;
* conclusion.

Each new document no longer started from a blank page.

Instead.

It started from a predefined structure.

---

## 3.4. The First True Standardization

For the first time.

Consistency no longer depended exclusively on the author.

It became a property of the document model itself.

This change immediately produced several improvements.

* more homogeneous documents;
* more predictable reading;
* simplified maintenance.

---

## 3.5. Growth of the Template Library

As new document types emerged.

New Templates also appeared.

For example.

```text id="ev3-1"

			Architecture Template

			Research Template

			Reference Template

			Specification Template

			README Template

```

The Template library gradually expanded.

---

## 3.6. The End of the Universal Template

Initially it was believed that a single Template would be sufficient.

It quickly became clear that this assumption was incorrect.

An architecture document has completely different requirements from a research document.

Document diversity required specialization.

---

## 3.7. Specialization

Templates then began evolving according to different objectives.

Each Template became optimized for a specific form of organization.

For example.

* architecture;
* research;
* reference;
* standards;
* specifications.

This specialization significantly improved the quality of the documentation being produced.

---

## 3.8. The First Benefits

The systematic use of Templates brought several advantages.

Among them.

* greater consistency;
* reduced creation time;
* predictable structure;
* reuse of best practices.

For the first time, a true documentation standard began to emerge.

---

## 3.9. The Evolution Problem

However.

A new difficulty soon appeared.

Whenever a Template was improved.

The remaining ones remained unchanged.

Furthermore.

Documents that had already been created continued using outdated structures.

Maintenance once again became increasingly complex.

---

## 3.10. The Search for Common Elements

While reviewing the various Templates, an important observation emerged.

Regardless of the document type.

Certain elements were always repeated.

For example.

* author;
* version;
* language;
* status;
* dates.

This discovery would prove to be decisive.

---

## 3.11. A Template Does Not Define a Document

Another important conclusion emerged during this phase.

A Template only organizes a document.

It does not define its meaning.

Two documents created from the same Template may represent completely different knowledge.

This distinction clearly separated.

* structure;
* content.

---

## 3.12. The Beginning of Abstraction

For the first time.

The research began moving away from individual documents.

Attention gradually shifted toward the concepts shared by all documents.

This change marked the beginning of the Documentation Framework's true architectural abstraction.

---

## 3.13. End of the Phase

By the end of this period.

Templates had become widely adopted.

Documentation exhibited a much higher level of structural consistency.

However.

Several fundamental components were still missing.

* identification;
* Metadata;
* classification;
* traceability.

Templates addressed only structural organization.

---

## 3.14. Historical Milestone

**First formalization of document structure through reusable Templates.**

This moment marks the birth of the first permanent component of the Documentation Framework.

---

## 3.15. Consequences

A comparative analysis of the different Templates led directly to an unexpected discovery.

A significant portion of the information repeatedly appearing in documents was not part of their content.

Instead.

It described the document itself.

This observation paved the way for the concept of **Metadata**, one of the fundamental pillars of the Documentation Framework.

---

## 3.16. Next Phase

The next phase would be dedicated to the discovery and formalization of **Metadata**.

For the first time.

Documents would no longer be viewed solely as organized content.

They would also possess their own intrinsic properties.

This evolution would profoundly transform the entire documentation architecture.

---

## 3.17. Phase Summary

| Aspect | Status |
| ------- | ------ |
| Organization | Structured |
| Conventions | Formalized |
| Templates | Established |
| Metadata | Under Discovery |
| Document Identity | Nonexistent |
| Workflow | Nonexistent |
| Registry | Nonexistent |
| Baselines | Nonexistent |
| Document Relationships | Implicit |

---

## 3.18. Conclusion

The introduction of Templates marked the first major evolutionary step in documentation.

Document creation no longer depended exclusively on the experience of individual authors and instead became based on structured, reusable models.

More importantly.

It was during this phase that the realization emerged that every document shared a common layer of information.

This discovery would lead directly to the introduction of **Metadata**, marking the beginning of a new stage in the evolution of the Documentation Framework.

---

# 4. Metadata Standardization

---

## 4.1. Introduction

The consolidation of Templates significantly improved the structural organization of the documentation.

However.

During their practical use, a recurring observation began to emerge.

Regardless of the document type, there was always a common set of information.

This information did not describe the knowledge itself.

It described the document.

It was precisely this discovery that led to the process of **Metadata standardization**.

---

## 4.2. Primary Objective

The objective was no longer simply to organize documents.

It also became necessary to organize the information about those documents.

This represented a significant conceptual evolution.

---

## 4.3. Repeated Information

After analyzing dozens of documents, it became evident that many elements were repeatedly present.

For example.

* author;
* version;
* date;
* language;
* status;
* project.

Although these elements appeared in nearly every document.

There was no consistent standard for them.

---

## 4.4. Initial Attempts

Initially.

Each Template began to include a small header.

For example.

```text id="ev4-1"

			Title

			Author

			Version

			Date

```

This solution reduced some inconsistencies.

However, it quickly revealed new limitations.

---

## 4.5. The Need for Uniformity

A new concern then emerged.

Should every document use exactly the same fields?

Or should different Templates be allowed to define their own?

After several experiments.

A common minimum set of fields was identified.

This core gradually became mandatory.

---

## 4.6. The Metadata Concept

It was during this phase that the term **Metadata** began to be used systematically.

Metadata came to represent all the information that describes a document.

But does not belong to its content.

This distinction became a permanent principle of the framework.

---

## 4.7. The Document Header

Document headers gradually evolved into a stable structure.

For example.

```text id="ev4-2"

			Document ID

			Title

			Version

			Status

			Project

			Language

```

This organization quickly became recognizable throughout the documentation.

---

## 4.8. Separating Content from Structure

One of the most important decisions made during this phase was the clear separation between.

* knowledge;
* administrative information.

The content became the body of the document.

Metadata was assigned its own dedicated section.

This separation significantly improved readability.

---

## 4.9. Immediate Benefits

Metadata standardization delivered several immediate benefits.

Among them.

* faster document identification;
* greater consistency;
* simplified review processes;
* preparation for future automation.

Although no dedicated tools yet existed.

The architecture was clearly evolving in that direction.

---

## 4.10. Next Step

The next phase would focus on the formalization of **Metadata**.

For the first time.

Documents would no longer be regarded solely as organized content.

They would also be recognized as entities with their own properties.

This evolution would profoundly transform the entire document architecture.

---

## 4.11. Phase Summary

| Aspect | Status |
| ------- | ------ |
| Organization | Structured |
| Conventions | Formalized |
| Templates | Consolidated |
| Metadata | Under Discovery |
| Document Identity | Non-existent |
| Workflow | Non-existent |
| Registry | Non-existent |
| Baselines | Non-existent |
| Document Relationships | Implicit |

---

## 4.12. Conclusion

The introduction of Templates marked the first major evolutionary step in the documentation.

Document creation no longer depended exclusively on the experience of individual authors, but instead relied on structured and reusable models.

More importantly.

It was during this phase that the realization emerged that every document shared a common layer of information.

This discovery led directly to the emergence of **Metadata**, initiating a new stage in the evolution of the Documentation Framework.

---

# 5. Document Identity

---

## 5.1. Introduction

The standardization of Metadata solved an important problem.

Documents now possessed consistent properties.

However.

A new challenge quickly emerged.

How can a document be identified throughout its entire existence?

Until then.

Identification depended on the document title.

Or on its filename.

Both approaches proved to have significant limitations.

This phase marks the emergence of the concept of **Document Identity**.

---

## 5.2. Primary Objective

The objective was to assign a permanent identity to every document.

Regardless of.

* changes to its title;
* changes to its directory location;
* evolution of its content;
* version updates.

Identity became a permanent property.

---

## 5.3. The First Identifiers

The earliest experiments used simple identifiers.

For example.

```text id="ev5-1"

			DOC-001

			DOC-002

			DOC-003

```

Although they solved the uniqueness problem.

They conveyed no meaning.

---

## 5.4. The Search for Semantic Identifiers

A new idea then emerged.

Perhaps an identifier could also communicate information.

For example.

* domain;
* category;
* purpose.

This approach would allow part of the document's meaning to be understood simply by reading its identifier.

---

## 5.5. The Emergence of Families

The first major evolution was the introduction of **Families**.

For example.

```text id="ev5-2"

			META

			ARC

			ANL

			REF

			STD

```

Each Family came to represent a major documentation domain.

This classification proved to be extremely effective.

---

## 5.6. The Introduction of Types

It soon became apparent that the Family alone was still too generic.

A second level was therefore introduced.

The **Types**.

For example.

```text id="ev5-3"

			META-DCL

			META-WFL

			META-REF

			META-CON

```

The combination of Family and Type made it possible to identify not only the document's domain.

But also its purpose.

---

## 5.7. Sequential Numbering

Once Families and Types had been established.

A sequential numbering system was introduced.

Conceptually.

```text id="ev5-4"

			META-DCL-001

			META-DCL-002

			META-DCL-003

```

This model produced identifiers that were.

* unique;
* readable;
* stable;
* semantically meaningful.

---

## 5.8. The Concept of Class

Another important evolution was the introduction of **Document Classes**.

Classes came to represent the nature of a document.

For example.

* Architecture;
* Reference;
* Research;
* Standard;
* Workflow.

This additional level significantly improved organizational capabilities.

---

## 5.9. Permanent Identity

It was during this phase that a fundamental principle was established.

A document identifier must never change.

Even if.

* the title changes;
* the document is reorganized;
* new versions are published.

Identity became permanent.

---

## 5.10. Document and File

Another important distinction naturally emerged.

The document was no longer confused with the file.

The file represents a physical implementation.

The document represents a logical entity.

This separation profoundly transformed the document architecture.

---

## 5.11. Metadata Evolution

Metadata continued to evolve.

New fields became part of the document header.

For example.

```text id="ev5-5"

			Document ID

			Family

			Type

			Class

			Version

			Revision

			Status

```

Identity became an integral part of the document structure.

---

## 5.12. The First Automation Possibilities

With permanent identifiers in place, new possibilities also began to emerge.

For example.

* automatic reference generation;
* document validation;
* category-based navigation;
* index generation.

Although still at an early stage.

These ideas laid the foundation for the future Registry.

---

## 5.13. End of the Phase

By the end of this period.

Documents now possessed.

* permanent identity;
* formal classification;
* consistent document structure.

The Documentation Framework was no longer managing only files.

It was managing document entities.

---

## 5.14. Historical Milestone

**Formal introduction of document identity through Document IDs, Families, Types, and Classes.**

This milestone represents one of the structural pillars of the entire document architecture.

---

## 5.15. Consequences

The creation of Document Identity immediately led to another requirement.

Some documents no longer described only the project.

They began describing the documentation itself.

This evolution would directly lead to the emergence of **META Documents**, responsible for formally defining the rules of the Documentation Framework itself.

---

## 5.16. Next Step

The next phase would focus on the birth of the META Documents.

For the first time.

The documentation would begin documenting its own rules, structures, and processes.

This milestone would mark the definitive transformation of documentation into a true architectural system.

---

## 5.17. Phase Summary

| Aspect | Status |
| ------- | ------ |
| Templates | Consolidated |
| Metadata | Standardized |
| Document Identity | Formalized |
| Families | Introduced |
| Types | Introduced |
| Classes | Introduced |
| Workflow | Non-existent |
| Registry | Non-existent |
| Baselines | Non-existent |
| Document Relationships | Implicit |

---

## 5.18. Conclusion

The formalization of **Document Identity** represented one of the greatest advances in the evolution of the Documentation Framework.

By permanently separating identity, content, and physical location, documents acquired their own logical existence, independent of how they were stored.

This evolution created the foundation for every capability that followed, from the Registry to Baselines and ultimately the Knowledge Graph.

It was also during this phase that a decisive idea began to emerge: some documents would no longer describe the project itself, but instead describe the documentation system, giving rise to the future **META Documents**.

---

# 6. META Documents

---

## 6.1. Introduction

The formalization of **Document Identity** fundamentally transformed the architecture of the Documentation Framework.

Documents now possessed their own permanent identity.

However.

As the framework continued to evolve, a new category of documents began to emerge.

These documents did not describe components.

Nor algorithms.

Nor architecture.

They described the documentation itself.

This milestone marks the emergence of the **META Documents**, one of the most significant developments in the evolution of the Documentation Framework.

---

## 6.2. Primary Objective

The objective was to formally define the rules governing the documentation itself.

Until this point.

Most of these rules existed only as experience accumulated throughout the project.

They needed to become explicit.

---

## 6.3. The First Rules

Initially, a number of small conventions began to be documented.

For example.

* how documents should be identified;
* how Templates should be organized;
* how document headers should be structured;
* how documents should be numbered.

These rules no longer existed solely in the authors' experience.

---

## 6.4. The Birth of the META Family

A new document Family was then introduced.

```text id="ev6-1"

			META

```

This Family represented an entirely new concept.

Documents whose knowledge domain was the Documentation Framework itself.

---

## 6.5. The First META Document

The first META Documents emerged to address specific needs.

For example.

```text id="ev6-2"

			META-DCL

			Documentation Classification

```

Its objective was to formally define.

* categories;
* types;
* conventions;
* classification rules.

This became one of the first truly foundational documents of the framework.

---

## 6.6. The Growth of the META Family

As new requirements emerged.

Additional META Documents were created.

For example.

```text id="ev6-3"

			META-DCL

			META-REF

			META-CON

			META-WFL

```

Each document was assigned a clearly defined responsibility.

---

## 6.7. From Convention to Specification

An important shift occurred during this phase.

The rules ceased to be simple recommendations.

They became formal specifications.

Every decision became.

* documented;
* versioned;
* traceable.

This formalization significantly increased the stability of the documentation system.

---

## 6.8. The Architecture of Documentation

Another important consequence was the emergence of a dedicated architecture for the documentation itself.

The META Documents also became interconnected.

For example.

```text id="ev6-4"

				 META-DCL

					↓

				   uses

					↓

				 META-REF

					↓

			   complements

					↓

				 META-CON

					↓

				relates to

					↓

				 META-WFL

```

The documentation definitively ceased to be a collection of independent documents.

---

## 6.9. The Framework Becomes Self-Describing

For the first time.

The Documentation Framework became capable of explaining its own operation.

Every architectural decision concerning the documentation was now expected to have its own dedicated document.

This objective became a permanent principle of the framework.

---

## 6.10. The Evolution of the Rules

Another important observation emerged.

The rules themselves also evolve.

Consequently.

META Documents also acquired.

* versions;
* revisions;
* lifecycle states;
* change history.

The framework had begun documenting the evolution of its own decisions.

---

## 6.11. Meta-Knowledge

During this phase.

A new level of abstraction also emerged.

META Documents do not describe technical knowledge.

They describe knowledge about knowledge.

This characteristic brought the Documentation Framework closer to the classical concepts of metamodeling.

---

## 6.12. Consolidation

By the end of this phase.

The META Family had become fully integrated into the document architecture.

The remaining documents progressively became governed by the rules it defined.

Document consistency improved significantly.

---

## 6.13. End of the Phase

The Documentation Framework now provided.

* document identity;
* standardized Metadata;
* consolidated Templates;
* its own document architecture;
* documentation of its own rules.

The system was clearly beginning to exhibit the characteristics of an infrastructure.

---

## 6.14. Historical Milestone

**Formal creation of the META Family and the first META Documents.**

This milestone represents the transformation of the documentation into a system capable of defining and governing its own rules.

---

## 6.15. Consequences

The existence of well-defined documentation rules naturally led to a new concern.

How can we ensure that every document follows those rules?

How can their evolution be controlled?

These questions would directly lead to the emergence of the **Document Workflow**, responsible for formalizing the lifecycle of documents.

---

## 6.16. Next Step

The next phase would focus on the development of the **Document Workflow**.

Documents would no longer evolve informally.

Instead, they would follow a clearly defined process based on states, transitions, and responsibilities.

This would become another fundamental pillar of the Documentation Framework.

---

## 6.17. Phase Summary

| Aspect | Status |
| ------- | ------ |
| Templates | Consolidated |
| Metadata | Standardized |
| Document Identity | Formalized |
| META Family | Created |
| META Documents | Introduced |

# 7. Documentation Workflow

---

## 7.1. Introduction

The creation of the **META Documents** made it possible to formalize the rules of the Documentation Framework.

However.

An important problem still remained.

The rules defined **how** a document should be structured.

But they did not define **how** that document should evolve over time.

It was precisely this need that led to the creation of the **Documentation Workflow**.

This phase marks the introduction of the document lifecycle concept.

---

## 7.2. Primary Objective

The objective became the control of document evolution.

Until this point.

Changes were made freely.

Without any formal process.

A predictable evolution process needed to be established.

---

## 7.3. The First Experiments

Initially, a very simple model was adopted.

```text id="ev7-1"

				  Draft

					↓

				 Approved

```

Although functional.

Its limitations quickly became apparent.

Between an initial idea and its approval, several important stages were missing.

---

## 7.4. Introducing the Review Stage

The next step consisted of introducing an intermediate phase.

```text id="ev7-2"

				  Draft

					↓

				  Review

					↓

				 Approved

```

The review stage became a fundamental part of the process.

Documents no longer depended exclusively on the author's own evaluation.

---

## 7.5. The Concept of State

During this phase, it became evident that a document possesses its own lifecycle state.

Regardless of its version.

Formal document states began to emerge.

For example.

```text id="ev7-3"

			Draft

			Review

			Approved

			Deprecated

			Archived

```

This lifecycle model remained virtually unchanged throughout the following phases.

---

## 7.6. State and Version

An important distinction was formalized.

A version describes the evolution of the document's content.

A state describes the maturity of the document.

Although they are often used together.

They represent completely different concepts.

This separation became a permanent principle of the framework.

---

## 7.7. Workflow as a Process

Another important evolution was the transition from viewing the Workflow merely as a sequence of states.

It became understood as a process.

Every transition became governed by well-defined rules.

For example.

* a document must be reviewed before it can be approved;
* archived documents cannot return to the Draft state;
* deprecated documents are excluded from future Baselines.

---

## 7.8. Introducing Responsibilities

As the Workflow evolved, another requirement emerged.

Not every transition should be performed by the same person.

Different roles were therefore introduced.

For example.

* Author;
* Reviewer;
* Owner;
* Approver.

The Workflow now incorporated responsibilities as well as states.

---

## 7.9. Immediate Benefits

The formalization of the Workflow brought several improvements.

Among them.

* greater consistency;
* improved traceability;
* systematic reviews;
* fewer errors.

The overall quality of the documentation increased significantly.

---

## 7.10. Preparing for Automation

Another important consequence was the possibility of automating the documentation process.

For example.

A tool could prevent.

* approval without review;
* publication of incomplete documents;
* use of deprecated documents.

The Workflow was no longer merely a procedure.

It became an executable process.

---

## 7.11. Integration with the META Documents

The META Documents also continued to evolve.

They became the formal specification for.

* lifecycle states;
* transitions;
* responsibilities;
* Workflow rules.

The process itself became documented.

---

## 7.12. The Document Lifecycle

By the end of this phase.

The concept of the document lifecycle had been fully established.

Every document now possessed.

* creation;
* evolution;
* stabilization;
* deprecation;
* archival.

Documentation had begun to behave like any other engineering asset.

---

## 7.13. End of the Phase

The Documentation Framework now included.

* formal rules;
* a defined Workflow;
* document lifecycle states;
* responsibilities;
* a review process.

Document management was becoming progressively more mature.

---

## 7.14. Historical Milestone

**Formal introduction of the Documentation Workflow and the document lifecycle.**

This milestone represents the transition from static documentation to a process-driven documentation system.

---

## 7.15. Consequences

The existence of lifecycle states and versions quickly revealed another requirement.

How can we ensure that a collection of documents represents a consistent state of the documentation?

This question would directly lead to the emergence of **Baselines**, responsible for representing stable states of documented knowledge.

---

## 7.16. Next Step

The next phase would focus on the creation of **Baselines** and the document version management system.

Documents would no longer evolve only individually.

They would also become part of consistent collections of knowledge.

# 8. Registry and Catalog

---

## 8.1. Introduction

The introduction of the **Documentation Workflow** solved the problem of managing the individual evolution of documents.

However.

As the documentation continued to grow, another limitation became evident.

Documents were properly structured.

They possessed identity.

They possessed lifecycle states.

Yet locating them and understanding their relationships became increasingly difficult.

It was precisely this need that gave rise to the **Document Registry**.

---

## 8.2. Primary Objective

The objective was to create a centralized mechanism capable of representing the entire body of documentation.

Without depending on the physical organization of files.

The Registry came to be regarded as a documentation catalog.

---

## 8.3. The Directory Problem

Until this point.

The location of documents depended primarily on the directory structure.

For example.

```text id="ev8-1"

			docs/

			architecture/

			meta/

			research/

			reference/

```

Although useful.

This organization had significant limitations.

Directories organize files.

They do not organize knowledge.

---

## 8.4. The First Ideas

Proposals soon emerged to create a centralized index.

Each document would have an entry containing its essential information.

For example.

* Document ID;
* title;
* Family;
* Type;
* status;
* version.

Thus, the first concept of the Registry was born.

---

## 8.5. The Registry as a Catalog

Initially.

The Registry functioned primarily as an inventory.

Allowing questions such as.

* Which documents exist?
* Which documents belong to the META Family?
* Which documents describe the architecture?

To be answered quickly.

This functionality proved immediately valuable.

---

## 8.6. The Growth of the Catalog

As new documents were created.

The Registry also expanded.

The catalog quickly became the primary entry point to the documentation.

Users began consulting the Registry first.

And only then the individual documents.

---

## 8.7. Separating the Document from the Registry Entry

An important architectural decision was formalized.

The document and its corresponding Registry entry represent different entities.

Conceptually.

```text id="ev8-2"

				 Document

					↓

			  Represented by

					↓

			  Registry Entry

```

This separation made it possible to evolve both independently.

---

## 8.8. More Than an Index

Over time.

The Registry assumed additional responsibilities.

Beyond locating documents.

It also enabled.

* classification;
* searching;
* filtering;
* navigation.

The catalog gradually evolved into a core documentation infrastructure.

---

## 8.9. Discovering Relationships

During practical use, an important observation emerged.

Documents rarely exist in isolation.

Each document references several others.

The Registry therefore began storing information about these relationships as well.

This evolution directly prepared the next phase.

---

## 8.10. Preparing for Automation

Another important consequence was the possibility of automating numerous tasks.

For example.

* index generation;
* detection of missing documents;
* reference validation;
* documentation reporting.

The Registry came to be viewed as an active component of the framework.

---

## 8.11. Integration with Metadata

Metadata proved fundamental during this phase.

Much of the information stored in the Registry could now be extracted directly from document headers.

Consistency between documents and the catalog became almost automatic.

---

## 8.12. Consolidation

By the end of this phase.

The Registry was no longer merely a supporting file.

It had become a dedicated architectural layer.

The entire documentation ecosystem progressively came to depend upon it.

---

## 8.13. End of the Phase

The Documentation Framework now provided.

* Templates;
* Metadata;
* Document Identity;
* Workflow;
* a centralized Registry.

The documentation infrastructure had become significantly more mature.

---

## 8.14. Historical Milestone

**Introduction of the Document Registry as the central catalog of the documentation.**

This milestone represents the transition from directory-based organization to knowledge-based organization.

---

## 8.15. Consequences

As the Registry continued to grow.

It became evident that the true value lay not only in the documents themselves.

But also in the relationships between them.

This discovery would directly lead to the formalization of **Document Relationships** and the emergence of the **Knowledge Graph** concept.

---

## 8.16. Historical Milestone

**Formal introduction of Baselines as stable representations of documented knowledge.**

This milestone marks the transition from managing individual documents to managing coherent versions of the entire documentation ecosystem.

---

## 8.17. Consequences

The introduction of Baselines completed most of the structural architecture of the Documentation Framework.

However.

One important question still remained.

Why do documents evolve?

The answer was not found within documentation itself.

It was found in the process that governs change.

This realization would naturally lead to the integration of the **Change Management System (CMS)**, responsible for managing the origin, approval, and implementation of changes affecting the documentation.

---

## 8.18. Next Stage

The next phase would focus on integrating the Documentation Framework with the **Change Management System**.

For the first time.

Documentation would become part of a complete engineering process.

Documents would no longer evolve simply because they were edited.

They would evolve because approved changes required them to evolve.

This integration would complete the conceptual architecture of the Documentation Framework.

					↓

# 10. Baselines and Versioning

---

## 10.1 Introduction

The formalization of the **Knowledge Graph** made it possible to represent documents and their relationships as a coherent network of knowledge.

However.

One important question still remained.

Documentation evolves continuously.

How can a stable state of that evolution be represented?

How can it be ensured that a collection of documents corresponds to a consistent version of the knowledge?

These questions directly led to the emergence of **Baselines**.

This phase marks the introduction of formal document evolution management.

---

## 10.2. Main Objective

The objective was to represent stable states of the documentation.

Until then.

Each document had its own version.

But the document collection had no common identity.

This limitation needed to be addressed.

---

## 10.3. The Problem of Individual Versions

Consider the following scenario.

```text id="ev10-1"

			Document A → Version 3

			Document B → Version 7

			Document C → Version 2

```

These versions can coexist.

But they do not guarantee that they are mutually compatible.

The documentation required a higher-level concept.

---

## 10.4. The Baseline Concept

The concept of a **Baseline** was then introduced.

A Baseline represents a coherent set of approved documents.

Conceptually.

```text id="ev10-2"

			   Baseline 2.0

					↓

			   Document A v3

			   Document B v7

			   Document C v2

```

The Baseline came to represent a consistent state of knowledge.

---

## 10.5. Much More Than a Version

It soon became clear that.

A Baseline is not merely a collection of versions.

It also represents.

* approved decisions;
* stabilized architecture;
* consistent rules;
* validated knowledge.

Its significance proved to be much broader.

---

## 10.6. Stable States

Another important consequence was the ability to freeze specific moments in the evolution.

For example.

```text id="ev10-3"

			    Baseline 1.0

					↓

			    Baseline 2.0

					↓

				Baseline 3.0

```

Each Baseline came to represent a historical milestone in the documentation.

---

## 10.7. Integration with the Workflow

The Workflow also began to play an important role.

A simple principle was established.

Only approved documents can be included in a Baseline.

This rule ensured a high level of consistency.

---

## 10.8. Document Versioning

During this phase, it also became necessary to distinguish between.

* document version;
* revision;
* Baseline version.

Each level came to represent a different perspective of the evolution.

This separation made the system significantly more robust.

---

## 10.9. Traceability

Baselines also introduced a new level of traceability.

It became possible to answer questions such as.

* which documents were part of Baseline 2.0?
* when was a particular decision introduced?
* in which Baseline did a particular architecture first appear?

Historical management became much simpler.

---

## 10.10. Knowledge Consolidation

Another important realization was that.

Baselines represent stabilized knowledge.

While the Workflow manages individual documents.

Baselines manage complete states of the documentation.

This distinction proved to be extremely useful.

---

## 10.11. Coordinated Evolution

For the first time.

Documents no longer evolved only individually.

They also evolved as a collection.

This coordinated evolution brought the Documentation Framework closer to traditional configuration management systems.

---

## 10.12. Integration with the META Documents

The META Documents themselves also became part of Baselines.

The documentation rules evolved together with the rest of the knowledge.

The documentation became fully self-consistent.

---

## 10.13. Situation at the End of the Phase

By the end of this period.

The Documentation Framework included.

* Workflow;
* Registry;
* Knowledge Graph;
* Baselines.

Its main structural components were virtually complete.

---

## 10.14. Historical Milestone

**Formal introduction of Baselines as representations of consistent states of documented knowledge.**

This milestone definitively consolidated the management of document evolution.

---

## 10.15. Consequences

The existence of Baselines revealed a new opportunity.

The Documentation Framework had become sufficiently mature to evolve beyond being merely a documentation infrastructure.

It could now be integrated directly into the architecture of the **VisualEngine**.

This integration would represent the next phase of its evolution.

---

## 10.16. Next Stage

The next stage would be dedicated precisely to the integration between the Documentation Framework and the VisualEngine.

For the first time.

The documentation would no longer simply accompany the project.

It would become an integral part of its architecture.

The chronology presented throughout this document has described the evolution of the Documentation Framework from its earliest attempts at document organization to the consolidation of its architecture.

* Template consistency verification;
* detection of invalid references;
